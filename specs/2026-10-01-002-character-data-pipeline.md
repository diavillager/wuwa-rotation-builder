# 공명자 데이터 등록 기반과 동기화·검수 흐름

## 기능 목적

실제 공명자 데이터와 WebP 자산을 앱에 연결하고, 개발용 `wuwa-character-sync` 스킬로 후보 수집부터 사람 검수·최종 등록까지 반복 가능한 흐름을 만든다. 소수 공명자로 먼저 검증한 뒤 전체 등록으로 확장한다.

작업 브랜치는 `codex/character-data-pipeline`이다. 1단계 구현을 재검토하고 2단계의 스킬·후보 수집 도구를 구현한다. 실제 검수 UI와 공명자 등록은 3·4단계다. 제품 요구사항의 기준은 요구사항 체크리스트와 PRD이며 이 spec은 구현 순서를 구체화한다.

## 관련 PRD 요구사항

- `docs/requirements-checklist.md` 6절: 데이터 경로, 후보 수집, 실제 아이콘 검수, 필수 검증, 기존 검수 결과 보존.
- `docs/PRD.md` 13·14절: 공명자 데이터 파이프라인과 개발용 `wuwa-character-sync`의 두 실행 경로.
- PRD 8–10절: 진열 스킬과 일반 교체 공격·변주·반주의 의미 및 조작 규칙.
- PRD 12.2절: 현재 ID 데이터 → 최소 snapshot → missing의 참조 해석과 공개 ID 호환성.
- AGENTS.md I1–I5 및 데이터 무결성: 파일명이나 입력키로 스킬을 추론하지 않고 기존 Rotation을 재구성하지 않는다.

## 현재 구현과 연결 지점

아래는 작업 시작 시점의 상태다.

- `src/app/catalog.ts`에는 공명자 ID·이름·속성·스킬 목록과 사람이 지정하는 자동 행동 참조가 있다. 실제 자산 필드와 JSON 로더는 아직 없다.
- 일반 화면은 `emptyCatalog`, 개발 화면은 `demoCatalog`를 사용한다. 개발 데이터와 최종 검수 데이터를 구분한다.
- `src/domain/project.ts`는 최소 참조 snapshot을 보관하며 앱은 현재 catalog의 정확한 ID를 우선 사용한다.
- `src/assets/characters/`와 동기화 스크립트·검수 UI는 이 spec 작성 시점에 없다.

## 범위와 구현 순서

### 1단계: Character 데이터 계약·검증·앱 연결

- PRD의 의미에 맞는 Character JSON 타입과 순수 검증기를 정의한다. 원본 JSON의 `characterId`·`attribute`를 기존 catalog의 `id`·`element`로 변환하는 어댑터를 분리한다.
- 최종 JSON은 `src/assets/characters/{characterId}/data/{characterId}.json`, WebP는 같은 공명자의 `assets/`에 둔다.
- Character·Skill·asset의 참조 ID를 안정적으로 관리한다. 이름 수정이나 후보 순서 변화가 ID 변경을 일으키지 않게 한다. 공개된 ID는 삭제·rename보다 비활성화를 우선한다.
- 검수된 JSON과 자산을 읽어 파티 선택·초상화·스킬 진열·InputBlock/AutoAction 스킬 표시에 연결한다. 입력키만으로 스킬을 연결하지 않는다.
- 후보 자료를 앱의 최종 catalog로 직접 사용하지 않는다. 최종 데이터 계약 검증과 검수 상태를 확인하는 로딩 경계를 둔다.

#### 1단계 구현 계약과 확정된 오류 처리

- 최종 JSON은 `schemaVersion: 1`, `reviewStatus: approved`, `characterId`, `displayName`, `attribute`, `portrait`, `skills`, `autoActions`를 가진다. `approved`는 사람이 완료한 검수 기록이며 자동 검증이 의미를 승인하는 표시가 아니다.
- 각 스킬은 `skillId`, `displayName`, `visible`, `asset`을 가진다. 세 자동 행동은 노출·등록된 스킬 ID를 각각 명시적으로 참조한다. ID는 공명자 간에도 충돌하지 않는다.
- 자산 경로는 공명자 폴더 안의 `assets/*.webp`로 제한한다. 초상화와 노출 스킬의 파일 존재, HTTP 응답, Content-Type, RIFF/WebP 표식, 실제 이미지 디코딩과 크기를 확인한다.
- 안정적인 자산 ID와 Vite 표시 URL을 분리한다. 프로젝트 snapshot에는 안정적인 ID만 넣으며 URL은 저장하지 않는다.
- 이름이 있는 비노출 스킬은 기존 프로젝트의 정확한 ID 조회를 위해 catalog에 보존하되 진열에서는 제외한다. 비노출 이미지가 검증되지 않았다면 표시 URL을 연결하지 않는다.
- 사용자가 승인한 오류 처리: JSON 손상·필수 이미지 누락·검증 실패가 있는 공명자만 선택 목록에서 제외하고 ID와 오류를 표시한다. 정상 공명자는 계속 사용하며 기존 프로젝트의 저장된 이름·블록·순서·stage·suppression을 유지한다. ID 충돌은 관련 공명자를 모두 오류로 처리한다.
- JSON을 raw 문자열로 로드하여 손상된 JSON 하나가 전체 빌드를 막지 않게 한다. catalog 준비 후 프로젝트 세션을 연다. 개발용 demo 데이터는 최종 catalog와 분리한다.
- 이번 단계에는 실제 게임 데이터나 공통 UI 아이콘을 등록하지 않는다. 자산 디렉터리와 계약 안내만 마련한다. 실제 이미지에 대한 검수·화면 검증은 4단계에서 수행한다.

### 공통 UI 아이콘 수집·연결

- 웹사이트 UI 전반에 사용할 공통 아이콘 자산도 이번 범위에서 수집한다. 파티 편성·공명자 스킬·개막/반복 사이클 제목은 현재 사용 예시이며, 사용 범위를 필드 제목으로 제한하지 않는다. 이후 버튼·메뉴·상태 표시 등 다른 UI에도 활용할 수 있도록 관리한다.
- 어떤 아이콘을 사용할지는 사용자가 이미 구상한 선택을 따른다. 구체 아이콘·출처·파일 식별 정보는 전달받은 뒤 기록하며 에이전트가 임의로 다른 아이콘을 선택하지 않는다.
- 공통 UI 아이콘은 공명자 초상화·스킬 아이콘과 구분해 관리한다. Character JSON이나 자동 행동 매핑에 포함하지 않으며 `wuwa-character-sync`의 공명자 등록 완료 판정과도 분리한다.
- 수집 시 출처와 이용 조건, 파일 형식·실제 이미지 유효성을 확인하고 실패를 기록한다. 자산 목록과 UI 사용처 매핑을 분리해 사용처를 확장할 수 있게 한다. 수집한 모든 아이콘을 즉시 화면에 배치하는 것은 아니며, 실제 적용 대상·크기·색상·배치는 구현 시 사용자와 확인한다.

### 2단계: `wuwa-character-sync` 스킬과 수집 도구

- 저장소에서 재사용 가능한 스킬 문서와 지원 스크립트를 만든다. 실제 스킬 제작 시 `skill-creator` 지침을 읽고 적용한다.
- 실행 경로는 미등록 공명자 전체 동기화와 지정 공명자 재동기화다. 전체 모드의 구현·테스트와 모든 공명자의 실제 등록 완료를 구분한다.
- 등록 판정은 폴더 존재가 아니라 최종 JSON 존재·유효성·디렉터리 ID 일치에 기반한다.
- Encore 목록과 등록 목록을 비교하고 기본 정보·한국어 이름·속성·초상화 후보를 수집한다.
- Encore Character API와 WW_Data의 스킬 아이콘 후보 합집합을 수집한다. 후보 ID·출처·원본 식별 정보·자산 참조를 기록해 사람이 추적할 수 있게 한다.
- Encore api-v2 Resource의 WebP는 HTTP 성공, 기대 Content-Type, 실제 이미지 디코딩과 WebP 형식을 검증한다. 확장자나 응답 헤더만으로 성공을 판정하지 않는다.
- 파일명·path·suffix는 후보 탐색에만 사용한다. `QTE`, `A1`, `B3`, `Intro` 등으로 최종 이름·노출 여부·자동 행동 매핑을 확정하지 않는다.
- 외부 API의 정확한 주소·응답 구조·이용 조건은 구현 시 실제 확인한다. PRD의 과거 spike 기록을 현재 API 접근 성공의 증거로 간주하지 않는다.

#### 2단계 구현 방법

- 저장소의 `.agents/skills/wuwa-character-sync/SKILL.md`와 `scripts/character-sync/`를 사용한다. Node.js·TypeScript(`tsx`)로 실행하고 `sharp`의 실제 픽셀 디코딩으로 WebP를 검증한다. 앱 번들에는 이 개발 도구를 포함하지 않는다.
- `--all --plan`은 Encore 목록과 로컬 최종 JSON·필수 이미지 검증 결과를 비교해 미등록·손상 대상을 보고한다. `--all`은 그 대상을 수집하고 `--character <ID>`는 지정 공명자를 재수집한다. 대상은 Encore 목록의 ID로 확인한다.
- 현재 확인한 Encore의 한국어 목록·상세 API와 api-v2의 `/resource/Data/Game/...webp`를 사용한다. WW_Data는 실행 시 기본 branch HEAD를 40자리 commit으로 고정하고 기록한다. `--ww-ref <commit>`으로 재현할 수 있다.
- WW_Data의 `roleinfo.SkillId → skill.SkillGroupId`, `skillbutton.RoleId → SkillIconTags → skillicon.Tag` 참조와 Encore에서 발견한 전용 아이콘 폴더를 후보 탐색에 사용한다. 이 연결은 수집 근거이며 최종 스킬 의미를 확정하지 않는다. 공용 `SkillIconNor` 폴더 전체는 특정 공명자의 전용 후보로 취급하지 않는다.
- 원본 이미지 경로를 정규화해 동일 자산의 후보를 합치고 모든 출처·원본 ID·필드·후보 이름을 보존한다. 후보 ID는 경로 기반 hash이며 최종 Skill ID와 별개다. 같은 그림의 다른 경로는 자동으로 의미를 합치지 않는다.
- 초상화 후보, 기본 정보 초안, 후보 목록, 원본 응답, 다운로드 성공·실패와 기존 검수 파일의 원문·hash를 `.character-sync/runs/<고유 실행 ID>/`에 저장한다. 이 폴더는 Git에서 제외한다. 재실행은 새 폴더를 만들어 이전 초안도 보존한다.
- 새 후보의 `displayName`, `visible`, 세 자동 행동은 미결정 상태로 둔다. 외부 후보 이름은 출처 정보로만 기록한다. 최종 JSON과 기존 검수값은 수집 도구가 덮어쓰지 않는다.
- 요청에는 시간 제한을 두며 실패한 소스·후보를 명시하고 부분 실패는 실패 종료 코드로 보고한다. 후보 수집 성공 상태는 등록 완료를 뜻하지 않는다. 1단계의 브라우저 이미지 검증에도 시간 제한을 적용한다.
- 실제 연결 검증은 소량의 읽기·후보 다운로드로 제한하며 시범 등록 대상을 확정하는 행위로 간주하지 않는다. 실제 아이콘 선택·최종 반영은 3·4단계에서 진행한다.

### 3단계: 실제 아이콘이 보이는 로컬 검수 UI

- 개발용 검수 화면에서 후보별 실제 아이콘과 출처, 기존 검수 여부, 새 후보 여부, 수집·다운로드 실패를 확인할 수 있게 한다.
- 사람이 스킬의 `displayName`·노출 여부와 `normalSwitchAttack`·`intro`·`outro`를 각각 지정한다.
- 기존 검수 결과와 새 후보를 분리해 보여주고 재동기화가 기존 이름·노출 여부·자동 행동 매핑을 덮어쓰지 않게 한다.
- 최종 반영 전에 필수 검증 결과를 보여준다. 필수 항목이 누락되면 완료로 처리하지 않는다.
- 검수 UI의 구체 레이아웃과 저장·확정 조작은 구현 전에 사용자와 결정한다. 이 spec에서 최종 UX로 확정하지 않는다.

### 4단계: 소수 공명자로 전체 흐름 검증

- 시범 대상은 사용자와 결정한 뒤 수집한다. PRD에 기록된 세 spike 공명자는 후보일 뿐 이번 등록 대상으로 자동 확정하지 않는다.
- 후보 수집 → WebP 검증 → 사람 검수 → 최종 JSON 반영 → 앱에서 파티·스킬 편집 → 프로젝트 저장·복원을 검증한다.
- 일반 교체 공격, 협주 반주·변주, suppression 보존을 실제 검수 데이터로 확인한다.
- 한 공명자를 재동기화해 기존 검수 결과와 ID가 보존되는지 확인한다.
- 이 흐름이 안정된 뒤 전체 대상 목록과 기준 시점을 정해 등록을 확대한다. 전체 등록 완료는 별도 후속 작업이다.

## 비범위 / 이번 작업에서 하지 않는 것

- JSON Import/Export와 PNG/JPG Export. 실제 데이터 시범 등록 이후 별도 Export spec에서 함께 계획한다. JPG 지원 여부는 아직 확정하지 않는다.
- 모든 공명자의 등록 완료, 첫 배포, 배포 대상 공명자 전체 목록 확정.
- 입력키나 파일명으로 스킬 의미를 자동 확정하는 기능, 자동 DPS·협주 게이지 계산·추천.
- 런타임에서 외부 API에 의존하는 동기화, 로그인·클라우드 저장.
- 기존 프로젝트를 최신 Character 데이터로 자동 재작성하는 migration.

## 사용자 동작 및 UX

앱 사용자는 기존 파티 선택창에서 검수된 공명자를 선택하고 활성 라인의 스킬을 직접 InputBlock에 연결한다. 속성 순서와 기존 입력·편집·교체 규칙은 유지한다. 파일명은 제품 UI에 노출하지 않는다.

개발자는 동기화 스킬에서 실행 경로와 대상을 지정하고 수집 결과·실패 목록을 확인한 뒤 로컬 검수 화면에서 의미를 확정한다. 새 후보와 기존 결과를 구분해 검수하며, 기본 재동기화로 검수 결과를 초기화하지 않는다. 구현 단계에서 질문이 필요한 미확정 조작은 아래 decision point에 둔다.

## 도메인 데이터에 미치는 영향

- Character catalog와 자산 참조를 확장하지만 Rotation의 Timeline·Transition·AutoAction·stage·suppression 저장 의미는 바꾸지 않는다.
- 공명자 ID를 소유권으로 사용한다. 파티 재정렬·저장·복원 후에도 의미상 소유 공명자를 유지한다.
- Character 업데이트만으로 기존 행동 순서나 자동 행동을 재생성하지 않는다. suppression을 지우지 않으며 새 자동 행동은 기존 명시적 교체 명령에 의해서만 생성한다.
- 기존 참조는 정확한 ID로 조회하고 현재 데이터가 없으면 최소 snapshot 또는 missing을 사용한다. 유사 이름·다른 스킬로 대체하지 않는다.
- catalog 로딩은 Undo/Redo 편집 단계나 파티 변경 명령이 아니다. opening/repeat 독립성은 유지한다.

## 주요 구현 방법

다음은 역할별 예상 디렉터리다. 구현 시 저장소 구조와 스킬 제작 지침에 맞춰 세부 파일명을 정한다.

```text
src/assets/characters/{id}/data/{id}.json   최종 검수 데이터
src/assets/characters/{id}/assets/*.webp   검증된 자산
src/assets/ui/                           웹사이트 전반의 사용자 지정 공통 UI 아이콘
src/data/characters/                     타입·검증·catalog 어댑터
scripts/character-sync/                  외부 소스 수집·이미지 검증·최종 반영
.agents/skills/wuwa-character-sync/       개발용 스킬과 실행 안내
tools/character-review/                  로컬 검수 UI
```

- 후보 초안·수집 로그는 최종 catalog와 분리한다. 작업 디렉터리와 Git 추적 정책은 구현 시 정한다.
- 수집·검증·검수 상태·최종 반영을 분리해 네트워크 없이 fixture로 핵심 로직을 테스트한다.
- 부분 수집 실패를 명시하고 성공 후보와 함께 보고한다. 실패한 후보를 조용히 제거하거나 전체 성공으로 표시하지 않는다.
- 경로가 대상 공명자 디렉터리를 벗어나지 않는지 확인한다. 최종 파일은 검증을 통과한 뒤 반영하고 실패 시 기존 파일을 보존한다.
- 재동기화는 기존 결과와의 비교 자료를 만들며 원본 검수 파일을 수집 단계에서 덮어쓰지 않는다.

## 필수 검증과 예외

- `characterId` 존재·디렉터리 ID 일치, 한국어 표시 이름, 허용된 6속성 중 `attribute`, 유효한 portrait asset.
- 노출 스킬의 검수된 이름·유효한 WebP asset과 Skill ID 중복 없음.
- 세 자동 행동이 각각 지정되고 실제 선택·등록 Skill ID를 참조함.
- JSON 손상, ID 충돌, 잘못된 자산 참조, 원본 후보 삭제·변경, 네트워크 실패, HTML 오류 응답, 잘못된 Content-Type, 손상된 이미지, 미완료 검수.
- 일부 필수 항목만 충족한 공명자는 완료로 판정하지 않는다. 손상된 기존 등록 데이터는 오류로 보고하며 정상 등록으로 건너뛰지 않는다.
- 출시 전 외부 데이터·이미지 이용 조건과 게임 IP 재배포 여부를 별도 확인한다.

## 테스트 계획과 완료 기준

- Character 검증: 필수 누락, ID 불일치·중복, 속성 오류, 자산 누락, 자동 행동 참조 오류 거부.
- 수집 fixture: 두 소스 합집합·중복 처리, 실패 기록, 전체 미등록 탐지와 지정 재동기화.
- WebP: 정상 파일과 HTTP 오류·HTML 응답·헤더 오류·손상된 파일을 구분.
- 재동기화: 기존 이름·노출·자동 행동·공개 ID와 최종 파일을 보존함.
- 검수·반영: 실제 아이콘 표시, 미완료 검수의 완료 차단, 최종 반영 실패 시 기존 파일 보존.
- 앱 연결: 속성별 파티 선택, 활성 라인 스킬 진열, 수동 연결, 초상화·스킬 자산 표시.
- 공통 UI 아이콘: 수집 자산의 유효성과 확정된 UI 사용처의 표시를 검증하고, 제목 외 사용처로 확장해도 공명자 등록·스킬 참조·Rotation 저장 데이터에 영향을 주지 않음.
- Rotation 회귀: 소유권·Shared Timeline·일반/협주 교체·두 Cycle 독립·stage·suppression의 저장·복원 및 catalog 변경 전후 내용 보존.
- 소수 대상의 사람 검수 결과가 최종 파일에 반영되고 앱에서 편집·저장·복원되는 것을 확인한 뒤 단계 완료로 보고한다. 후보 수집 성공만으로 등록 완료라고 보고하지 않는다.
- 구현 완료 시 lint/test/format:check/build와 수집·자산 검증 명령을 실제 실행한다. 외부 수집 실패와 fixture 검증 결과를 구분해 보고한다.

## 남아 있는 미확정 사항

- 시범 등록 공명자와 이후 전체 등록의 기준 목록·시점.
- 웹사이트 UI에 사용할 사용자 지정 아이콘의 구체 목록·출처·파일 식별 정보와 실제 사용처·표시 배치. 필드 제목 외 사용처도 포함할 수 있다.
- 검수 화면 배치, 초안 저장과 최종 확정 조작, 기존 검수값의 수동 변경 방법.
- 후보 합치기에서 소스별 ID 충돌·동일 아이콘을 사람이 구분하는 구체 표시 방식.
- 외부 소스 변경에 따른 어댑터 갱신과 배포 시점의 이미지 재배포 조건 재확인. 현재 관찰 결과는 수집 도구 문서에 기록한다.
- JSON과 이미지 Export UI, JPG 지원 여부는 후속 Export spec에서 결정한다.

위 사항은 임의로 제품 동작으로 확정하지 않는다. 현재 단계에서 독립적으로 진행 가능한 데이터 계약·검증부터 구현하고, 다음 단계의 구현을 실제로 막는 결정은 그 전에 사용자에게 질문한다.
